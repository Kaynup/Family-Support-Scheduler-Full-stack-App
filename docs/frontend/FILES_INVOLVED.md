# Files Involved in the Frontend Sub-system

This document maps every file in the frontend layer,
organized by architectural role and responsibility.

---

## 1. HTML Pages

### frontend/index.html

The login screen. First page the user sees.

Structure: A single centered card containing a login form.
The form uses HTML5 pattern validation with hardcoded credentials
(admin / password123). On valid submission, the browser navigates
to dashboard.html via a standard GET request.

No JavaScript is loaded on this page. Validation is handled entirely
by the browser's built-in constraint validation API through the
pattern attribute on the input elements. The title attribute on each
input provides the hint text shown when validation fails.

The page shares styles.css with the dashboard. Only the `.login-page`
and `.login-card` classes are relevant here. The dashboard-specific
styles (calendar, bill tables, modals) have no effect because the
corresponding HTML elements do not exist on this page.

### frontend/dashboard.html

The main application page. Contains all interactive components.

Structure: A two-column grid layout with a calendar panel and
due bills list on the left, and a search/action panel with paid
bills list on the right. Two modal overlays (create bill and
delete confirmation) are appended at the end of the main element,
hidden by default.

The page loads a single script tag: `<script type="module" src="js/dashboard.js">`.
The type="module" attribute is critical -- it enables ES6 import/export
syntax throughout the JavaScript layer and defers execution until
the DOM is fully parsed.

All interactive elements are identified by unique IDs, which are
registered in ui.js at module load time. The HTML defines the
structural skeleton; all dynamic content (calendar days, bill rows,
status text) is generated by JavaScript.

The calendar legend is defined in static HTML with inline styles
for the colored dots. This is the only part of the calendar that
is not generated by JavaScript. The legend's colors are hardcoded
to match the CSS glow classes.

The create modal form uses semantic HTML: labels are associated with
inputs via nesting (not via for/id), and the form uses native
required validation before JavaScript handles submission.

The delete modal is intentionally simpler -- no form element, just
a paragraph and two buttons. The confirmation text (#delete-confirm-text)
is updated dynamically by dashboard.js before the modal is shown.

## 2. Stylesheets

### frontend/styles.css

The main CSS entry point. It uses `@import` to load the modular CSS files.

### frontend/css/base.css

Base reset and core elements. Body uses CSS Grid with `place-items: center` for vertical and horizontal centering. The monospace font stack gives the application its technical aesthetic.

### frontend/css/layout.css

Structural layout. Defines the `main` container constraints and the `dashboard-grid`.

### frontend/css/components.css

UI building blocks. Contains the styling for cards, tables, and buttons.

### frontend/css/calendar.css

Calendar-specific styling. Defines the calendar grid and the "glow" system for bill statuses.

### frontend/css/modals.css

Overlay and modal content. Handles the background overlay and the centered content boxes.

## 3. JavaScript Modules

### frontend/js/core/state.js

The smallest module. Exports a single mutable object containing:
- selectedBill, currentMonth, currentYear, selectedDate, and projectionCount (controls how far into the future recurring bills are generated).
This module has no imports and no functions. It is pure shared state.

### frontend/js/core/api.js

The HTTP client layer. Exports wrapper functions for the backend API.
Handles JSON parsing, error extraction, and normalization of responses from `http://127.0.0.1:8000`.

### frontend/js/core/utils.js

The mathematical computation layer.
Contains `getProjectedBills()`, the critical function replacing old backend-driven recurrence logic. It projects future instances of WEEKLY/MONTHLY bills, using an anchor date strategy to prevent monthly drift (e.g., Feb 28th vs Jan 31st) and the Noon strategy to prevent timezone DST shifts.

### frontend/js/components/ui.js

The DOM interface layer. Exports the `elements` registry mapping HTML IDs to DOM references.
Also exports visual rendering functions like `showStatus`, `updateSelectedText`, `clearSelection`, and `renderList`, which builds tables dynamically.

### frontend/js/components/calendar.js

The calendar rendering engine.
`renderCalendar()` builds the entire grid, calculating month boundaries and mapping bills to specific days to apply CSS glow effects (`glow-paid`, `glow-expired`, etc.).

### frontend/js/components/modal.js

The modal lifecycle manager.
Toggles modal visibility (create, delete) and manages form defaults (like setting the minimum due date constraint).

### frontend/js/features/*

This directory holds the isolated business logic, mirroring the backend architecture:
- **billListing.js**: Orchestrates fetching data, calling the projection engine, and instructing the UI and Calendar components to update.
- **billStatus.js**: Handles the PATCH logic for marking bills as PAID/UNPAID.
- **billDeletion.js**: Manages the delete confirmation workflow.
- **billCreation.js**: Extracts form values and handles POST requests for new bills.
- **billSearch.js**: Handles the search bar input and rendering results.

### frontend/js/dashboard.js

The application entry point.
This file is minimal. It simply imports the features from `js/features/` and wires them to the DOM elements mapped in `js/components/ui.js`. It is the only script loaded directly by `dashboard.html`.
